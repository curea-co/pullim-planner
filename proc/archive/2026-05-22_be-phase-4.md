### 1.3 spec §3.3 인증 정의 vs 현재 helper (해석 (ii)·(iii) 대비)

### 1.4 spec §3.2 에러 코드 vs mutation 필요 surface

| 에러 surface | mutation에서 필요한 시나리오 | 5종 enum에 있나 |
|---|---|---|
| 필수 필드 누락·형식 오류 | POST/PATCH body 검증 실패 | `validation_failed` ✅ |
| 존재 안 함 | PATCH/DELETE/activate 대상 id 없음 | `not_found` ✅ |
| 다른 user의 planner mutation 시도 | userId !== planner.userId | `forbidden` ✅ |
| active 동시 변경 race | partial unique index 충돌 | `conflict` ✅ |
| active=true planner DELETE 시도 | spec §3 표 "active 차단" | `conflict` (현 enum 재사용) 또는 새 코드? |

→ "active planner DELETE 차단"은 `conflict`로 처리. 새 코드 추가 안 함 (5종 enum 보호).

### 추천 안 — A안

**이유**:
1. **spec §5 phase 정의가 권위**. daily_outcome A안의 "Phase 4 인증·RLS" 표현은 phase 슬롯 호명이 어긋난 것으로 해석(해석 (i)) — Phase 3와 동일 패턴(mutation만 한 phase) 유지
2. **현재 helper(auth/response/errors) 검증 surface**가 mutation 6+ route로 확장되는 게 본 phase의 핵심 가치. 강도 변경(B안)·인증 시스템 교체(C안)는 별 phase 응집성이 더 높음
3. **Ph8(NextAuth)·Ph9(Supabase RLS) 사전 도입은 결정 보류**(spec §6 "결정 보류"에 NextAuth provider·session strategy·prod DB 선택)에 의존 — 본 phase에 끌어들이면 *작업 단위가 결정 게이트에 막힘*
4. mutation 6+ route 정착 후 Ph5(block lifecycle)·Ph6(reports·condition) 추진이 자연스러움. Ph8/Ph9는 prod 직전(Ph7 FE 교체 완료 후) 1회 일괄 진행이 안전
