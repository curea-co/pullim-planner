플래너 서비스 / 풀림 플래너

학생용 학습 플래너 SaaS입니다. 프런트엔드(apps/planner)는 이 리포에 있고, 배포된 FE가 실제로 호출하는 성숙한 플래너 도메인 BE는 풀림(pullim) 플랫폼 API(pullim-api) 안에 있습니다. 아래 요청 경로·모듈 구조·엔드포인트·도메인 모델은 그 pullim-api 플래너 도메인 기준입니다 — 즉 이 리포의 흡수(adoption) 대상 상태입니다.

bun workspace 모노레포 FE Next.js 16 · React 19 · Tailwind v4 BE NestJS 11 · TypeORM · Postgres 16 · Redis 인증 쿠키 SSO · CSRF double-submit dev dev-planner.pullim.ai
두 개의 백엔드 — 혼동 주의. 이 문서가 그리는 BE는 pullim-api 플래너 도메인(라이브 dev-api.pullim.ai, 흡수 대상 상태)이다. 이와 별도로 이 리포 자체의 apps/backend 는 흡수 이전 단계의 placeholder 로, 아직 이 그림과 다르다 — 컨트롤러는 me · planners · blocks 뿐(routines·studygram·curriculum·dev-seed 없음), PK 는 Drizzle 시대 text(uuid 아님), Redis 미도입(refresh-token 블랙리스트를 Postgres 테이블로 대체). 아래 uuid·Redis·플랫폼 가드·studygram 표면은 모두 pullim-api 기준이며 apps/backend 현행이 아니다.

모듈 구조 — 클린 아키텍처

모든 BE 모듈이 이 형태를 미러
(예시: modules/routines)
controller 컨트롤러
HTTP 표면. 라우트, 가드, 요청/응답 DTO(controller/dto), Swagger 데코레이터(controller/swagger). HTTP ↔ use-case 입력을 변환한다.

연산 1개당 클래스 1개. 흐름을 조율한다 — 검증, 교차 엔티티 조회, 비즈니스 규칙(예: StudyProof 스냅샷 동결, 피드 RBAC). 구현체가 아닌 인터페이스에 의존.

Facade / 모듈 내 여러 use-case 가 공유하는 도메인 로직.

포트 — 리포지토리·의존성 계약(*-repository.interface.ts). use-case 를 TypeORM 으로부터 분리하는 의존성 역전 경계.
infrastructure 인프라
어댑터 — 포트를 구현하는 TypeORM 리포지토리, 엔티티 매핑, planner 스키마 대상 쿼리 빌드.
왜 반복되는가. routines 가 패턴을 확립했고, studygram(setting · proofs · friends · close-friends · reactions)이 그대로 복제했다. 가드 · CSRF · 엔타이틀먼트가 횡단 관심사라, 신규 도메인은 요청 파이프라인을 건드리지 않고 끼워 넣을 수 있다.

05

인증 + 변경 요청, 순서대로

왜 localhost 는 실패하고
*.pullim.local 은 되는가
1
미인증 감지 (클라이언트). 세션은 HttpOnly 쿠키라 RequireAuth 가 마운트 후 useAuth() 로 상태를 확인한다. 상태가 unauthenticated 이고 canCentralLogin() 이 true 일 때만 다음 단계로 간다. SSO 가능 호스트(pullim.ai / pullim.local)에서만 리다이렉트한다. SSO 불가 호스트(localhost / preview)나 env 미설정이면 리다이렉트 대신 안내 UI 를 띄운다(루프·크래시 방지). 세션 복원이 네트워크/5xx 로 실패한 error 상태는 로그인으로 보내지 않고 재시도 UI.
2
중앙 로그인으로 위임. <로그인 호스트>/login?next=<현재 URL> 로 리다이렉트. 로그인 호스트는 NEXT_PUBLIC_PULLIM_LOGIN_URL 로 환경마다 다르다 — prod 는 pullim.ai, 로컬은 pullim.local:3001. 고정 URL 이 아니다.
3
세션 쿠키 발급. 성공 시 플랫폼이 Domain=.pullim.ai 스코프의 HttpOnly 쿠키를 세팅하고 next 로 복귀시킨다. 플래너가 그 등록도메인을 공유하므로 쿠키는 same-site — 자동으로 함께 실려 간다. 로컬에선 *.pullim.local(/etc/hosts 매핑)이 상위 도메인을 공유하는 서브도메인 구성을 만들어 이를 흉내 낸다. 반면 맨 localhost 로는 그런 공통 상위 도메인의 서브도메인 구성(os.·api.·planner.)을 세울 수 없어, 서비스 간 쿠키 공유(SSO)를 재현하지 못한다.
4
CSRF 부트스트랩. 쓰기 요청 전에 GET /auth/csrf 가 토큰을 반환하고 non-HttpOnly CSRF 쿠키를 세팅한다(double-submit).
5
변경 요청. api-client 가 credentials:"include" 로 호출하며 토큰을 X-CSRF-Token 헤더로 되싣는다. BE 가드가 JWT(세션 쿠키) + CSRF(double-submit) + 엔타이틀먼트(flags.planner)를 검증한 뒤 쿼리를 user.sub 로 스코프한다.
검증 메모 (실제 코드 대조). 위 BE 내용은 pullim-api 플래너 도메인 실측 기준이며, 이 리포 apps/backend(흡수 이전 placeholder — 상단 콜아웃 참조)와는 다르다. pullim-api 유의점 — ① CSRF 가드는 쓰기(write) 엔드포인트에만 붙는다(@UseGuards(CsrfGuard, JwtVerifyGuard, EntitlementGuard('planner', { action: 'write' }))). 읽기는 Jwt + Entitlement(read). ② 엔타이틀먼트는 studygram 포함 현재 전부 flags.planner 를 쓴다. 공유용 별도 flags.studygram 은 plan 문서상 결정일 뿐 아직 코드 미반영(후속 항목). ③ 로컬 기본 포트 = planner 3030 · backend 4030; :3006 은 planner.pullim.local SSO 프록시 전용. ④ RequireAuth 는 서버 게이트가 아니라 클라이언트 마운트 후 세션 확인 → SSO 가능 호스트에서만 리다이렉트(그 외엔 안내 UI).
