## 1단계 — 갭 분석 매트릭스

### 1.1 spec §5 Ph3 정의 vs 현재 상태

| 산출물 | spec 정의 | 현재 | 갭 |
|---|---|---|---|
| `/api/me` | 현재 사용자(페르소나) | 미구현 | 코드 0건 |
| `/api/planners` | 시간표 목록 (active/inactive/archived) | 미구현 | 코드 0건 |
| `/api/planners/{id}/blocks?date=...` | 해당 날짜 블록 (오늘 default) | 미구현 | 코드 0건 |
| 인증 헤더 처리 | `X-User-Id` 또는 `student_001` fallback | 미구현 | helper 0건 |
| 응답 표준 | `{ data: T }` / `{ error: { code, message } }` | 미구현 | helper 0건 |
| 에러 코드 5종 | `not_found`/`validation_failed`/`conflict`/`forbidden`/`internal` | 미구현 | enum 0건 |

### 1.2 mock 함수 → endpoint 매핑 (FE 교체 대상 — Ph7 준비)

| endpoint | mock 함수 | mock 위치 | DB 소스 |
|---|---|---|---|
| `GET /api/me` | `currentPersona` | `src/lib/mock/persona.ts` | `users` (1 row) |
| `GET /api/planners` | `planners` (배열) + `getPlanners()` 류 | `src/lib/mock/planner.ts:835~` (3건) | `planners` + `planner_subject_units` join |
| `GET /api/planners/{id}/blocks?date=YYYY-MM-DD` | `todayBlocks` (기본) | `src/lib/mock/planner.ts` | `time_blocks` + `block_completions` left join, `planner_id = {id} AND date = {date}` |

### 1.3 인접 phase 침범 위험

- **Ph4 (mutation)**: 같은 `/api/planners` path에 POST·PATCH·DELETE 추가됨 → 본 phase는 GET handler만, 같은 파일에 export로 후속 phase 자연 추가
- **Ph6 (reports)**: `/api/planners/{id}/blocks?from=...&to=...`는 spec §3에 표기됐지만 주간·월간 조회 → 본 phase는 `?date=` 단일 일자만, `?from/to=`는 Ph6으로 분리
- **Ph7 (FE 교체)**: 본 phase는 endpoint 신설만. FE는 mock 함수 그대로 — `src/lib/api/` 도입 안 함

### 1.4 인증·검증 경계

- spec §3.3 mock 인증: `X-User-Id` 헤더 또는 cookie. 현 단계는 헤더만 + fallback `student_001` (seed가 single user라 fallback이 곧 default user)
- planner 소유자 검증: spec §3.2 `forbidden (403)` — Ph3에서는 read만이지만 `userId !== planner.userId` 차단 필요
- 날짜 파라미터 검증: `date=YYYY-MM-DD` 형식 검증 → 실패 시 `validation_failed (422)`

## 2단계 — fix 후보 3안

### 후보 A — spec Ph3 정의 그대로 (3 endpoint, 최협소) ⭐ 추천

**범위**: `/api/me` + `/api/planners` + `/api/planners/[id]/blocks?date=...` 3개 route handler만 구현

**구조**:
```
src/app/api/
  _lib/
    auth.ts           // getUserId(req): X-User-Id || 'student_001'
    response.ts       // ok(data), error(code, message, status)
    errors.ts         // ApiErrorCode enum + status mapping
  me/route.ts         // GET
  planners/route.ts   // GET (POST는 Ph4)
  planners/[id]/blocks/route.ts  // GET (POST는 Ph5)
```

**트레이드오프**:
- ✅ spec phase 정의 보호 (Ph4·Ph5 진행 패턴 유지)
- ✅ 1 PR 사이즈 작음 (3 endpoint + 3 helper = 6 파일 신규)
- ✅ helper 패턴이 후속 phase 그대로 재사용
- ❌ FE 입장에서 "오늘 화면" 1회 fetch에 3개 endpoint 필요 (`/api/me` + `/api/planners` + `/api/planners/{active}/blocks`) — `/api/conditions/today`·`/api/burnout/today`도 별도

### 후보 B — today 화면 1회 fetch 정합 (5 endpoint, 중간)

**범위**: A안 + `/api/conditions/today` + `/api/burnout/today` (read만)

**구조**: A안 + `src/app/api/conditions/today/route.ts` + `src/app/api/burnout/today/route.ts`

**트레이드오프**:
- ✅ today 화면 데이터 묶음 정합 (FE 교체 시 5 fetch로 끝)
- ✅ DailyCondition·BurnoutSnapshot 테이블 read 패턴 1회 정착
- ❌ Ph6 영역 일부 선제 침범 (spec §5 Ph6: condition·burnout·report 집계)
- ❌ PR 사이즈 1.7배 (5 endpoint + helper)

### 후보 C — 전 도메인 read 일괄 (확장, 최광범)

**범위**: B안 + `/api/curriculum?subject=...` + `/api/pedagogy-engines` + `/api/reports/day?date=...` 등 read 전부

**트레이드오프**:
- ✅ 1 PR로 read endpoint 통합 완료
- ❌ spec phase 정의 완전 무시 (Ph6 reports 침범)
- ❌ PR 사이즈 3배 — 리뷰 부담, 회귀 시 원인 분리 어려움
- ❌ FE 교체(Ph7) 시 한 번에 갈아탈 게 아니라 점진 교체이므로 read 일괄 구현이 곧 사용 직결 아님

### 후보 비교 표

| 항목 | A안 (3 endpoint) | B안 (5 endpoint) | C안 (전 read) |
|---|---|---|---|
| 범위 | spec Ph3 정의 그대로 | + today 보조 2건 | + Ph6 read 일부까지 |
| PR 파일 수 | 6 (route 3 + helper 3) | 8 (route 5 + helper 3) | 14+ |
| spec phase 보호 | ✅ | ⚠️ 일부 침범 | ❌ |
| today 화면 fetch 정합 | △ (3 호출 필요) | ✅ | ✅ |
| 후속 phase 패턴 정착 | ✅ helper 1회 | ✅ helper 1회 | ✅ 단 한 번에 |
| 회귀 위험 | 낮음 | 중간 | 높음 |

### 추천 안 — A안

**이유**:
1. spec §5 phase 정의가 명시적으로 "Ph3 = 3 endpoint"라고 좁힌 결정을 했음 — 이 결정을 본 phase에서 깨지 않음
2. 본 phase의 핵심 산출물은 endpoint **갯수**보다 **helper 패턴**(auth·response·errors) 정착. 3 endpoint로도 패턴 검증 충분
3. B안의 condition·burnout은 Ph6에서 reports 집계와 함께 read·write 묶어 처리하는 게 도메인 응집성 더 좋음
4. FE 교체(Ph7) 시점에서 today 화면 fetch 정합이 필요해지면 그때 B안 추가 — **사용 시점에 결정**이 best

**후보 미정 시 추천 안으로 진행** (09:30 약속 명시 룰).
